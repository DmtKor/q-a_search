# Модуль 09 — Admin/Demo UI (продакшен-подобный интерфейс)

## Цель и ограничения

- **Цель:** веб-интерфейс, пригодный для повседневного использования и демо: навигация по разделам, списки с фильтрами, просмотр деталей по клику, создание и редактирование сущностей. Не «минимальная демо-страница», а структура и поведение, близкие к админке/продакшену.
- **Ограничение:** модули 00–08 не меняем. UI только клиент существующего API по OpenAPI.

## Принцип интеграции

- Все запросы к API с заголовком `Authorization: Bearer <token>`. Токен вводится в настройках UI, опционально сохраняется в `localStorage`.
- Базовый URL API настраивается (поле в настройках или конфиг при сборке); при пустом поле — запросы на текущий origin + `/api/v1` (см. уточнение 2).
- **Тип доступа определяется только токеном:** у приложения (App) и сотрудника (Staff) разные токены; бэкенд по токену возвращает 403 на staff-эндпоинтах для app-токена. Переключиться «галочкой» с app на staff в UI нельзя — нужен другой токен. Когда и как определять тип — см. **Уточнения** ниже.

## Уточнения (решения по спорным пунктам)

1. **Определение типа доступа (App / Staff)**  
   Делать **явную проверку при старте**, а не ленивое определение по факту запросов. При сохранении токена в настройках (или при первом заходе, если токен уже сохранён в localStorage) выполнять один проверочный запрос к staff-эндпоинту, например `GET /api/v1/cases?limit=1`. Ответ 200 → считать токен Staff, показывать все разделы меню. Ответ 403 → App, показывать только «Поиск». Так тип известен до первого действия пользователя, и меню сразу отображается корректно.

2. **Базовый URL по умолчанию**  
   Пустое поле «Базовый URL API» означает: запросы уходят на **`window.location.origin + '/api/v1'`** (то есть относительно текущего origin), а не буквально путь `/api/v1` без origin.

3. **Поиск — user_context (первая версия)**  
   В первой версии — **одно поле textarea** для ввода «сырого» JSON. Не несколько отдельных полей (user_id, department и т.п.). Так форма проще и подходит для произвольной структуры; отдельные поля можно добавить позже при фиксированной схеме.

4. **Экспорт кейсов — имя файла**  
   Имя файла экспорта — **с датой/временем**, например `cases-export-2025-02-17.json` или `cases-export-2025-02-17T14-30-00.json`, чтобы разные экспорты не перезаписывали друг друга при сохранении на диск.

5. **Раздача UI и модуль 08**  
   В рамках этой задачи **не обязательно** реализовывать раздачу через 08. Достаточно SPA в каталоге `web/` с возможностью раздачи отдельным сервером или nginx. Добавление в 08 маршрута вида `/app/*` → статика из `web/dist/` — **опционально** (на усмотрение реализации).

6. **401 и истёкший/невалидный токен**  
   При 401 показывать общий формат ошибки (HTTP-код, error.code, error.message, error.details) **и дополнительно** явно предлагать действие: ссылку или кнопку «Перейти в Настройки и обновить токен».

7. **Приложения — редактирование settings (первая версия)**  
   В первой версии достаточно **явных полей** для `search.default_top_k` и `search.confidence_threshold`; остальные ключи в `settings` показывать **read-only** (например сырой JSON или список ключей без редактирования). Полноценный JSON-редактор для произвольных ключей не обязателен в первой версии.

8. **Каталог проекта**  
   Предпочтительное имя каталога: **`web/`**. Альтернатива `ui/` допустима, но в спецификации закрепляем `web/`.

## Общая структура приложения

### Макет и навигация

- **Боковое меню (сайдбар)** с пунктами:
  - **Поиск** — форма поиска и результаты (доступно App и Staff).
  - **База знаний** (Кейсы) — только Staff.
  - **Тикеты** — только Staff.
  - **Приложения** — только Staff.
  - **Настройки** — токен, базовый URL API, при необходимости сохранение в localStorage. Текущий тип входа (App / Staff) — только отображается, определяется по API, не выбирается пользователем.
- При выборе раздела в основной области отображается соответствующий экран (список или форма). Заголовок страницы и хлебные крошки (при необходимости) однозначно указывают раздел и выбранный объект.
- Ошибки API показываются в едином формате: HTTP-код, `error.code`, `error.message`, при наличии `error.details` (тост, баннер или модальное окно — на усмотрение реализации, но формат один).

### «Пользователи» и токены

- В текущем API нет сущности «пользователь» и нет эндпоинтов создания/выдачи токенов. Есть **приложения (Apps)** и токены (хранятся в БД, создаются сидами/скриптами/будущим admin API).
- В UI раздел **«Приложения»** — это управление приложениями (клиентами): список, создание, редактирование, настройки. Создание **токенов** для приложений в API не предусмотрено; если позже в OpenAPI появится создание токена — в UI добавить подраздел или форму (например «Создать токен» внутри карточки приложения). Пока в настройках только ввод готового Bearer-токена (полученного вне UI).

## Раздел «Настройки»

- **Bearer token** — поле ввода (текст или password). Кнопка «Сохранить в браузере» записывает значение в `localStorage` (ключ, например, `demo_token`); при следующем открытии подставлять сохранённый токен.
- **Базовый URL API** — поле ввода (например `https://localhost:8080`). Пустое = запросы на `window.location.origin + '/api/v1'` (см. уточнение 2). Сохранение в `localStorage` по желанию.
- **Тип входа (App / Staff)** — не переключатель; определяется явной проверкой при сохранении токена или при первом заходе с сохранённым токеном (уточнение 1). В настройках вывести read-only строку «Текущий доступ: App» или «Текущий доступ: Staff».
- Без валидного токена запросы не отправлять или показывать сообщение «Введите токен в настройках».

---

## Раздел «Поиск»

- **Форма:** поле запроса (обязательно), категория (опционально, выпадающий список или ввод), количество результатов top_k (опционально, число), user_context (опционально — в первой версии одно поле textarea для ввода сырого JSON; см. уточнение 3).
- Кнопка «Искать» → `POST /api/v1/search` с телом по OpenAPI.
- **Результаты:**
  - Список **чанков**: для каждого — заголовок (title), краткий фрагмент текста (например первые 1–2 строки), confidence. По клику на элемент — развернуть или открыть блок с полным текстом чанка (поле `text` из ответа). Отображать `case_id` (например ссылкой на раздел «База знаний» с этим id, если режим Staff).
  - Если в ответе есть **ticket** — показать отдельный блок: «Создан тикет для ручной обработки» с id и url (ссылкой), чтобы сотрудник мог перейти в раздел «Тикеты» и открыть этот тикет.
- Ошибки (4xx/5xx) выводить в едином формате ошибки API.

## Раздел «База знаний» (Кейсы) — только Staff

### Список кейсов

- **Группировка по категориям:** кейсы отображать сгруппированными по полю `category` (аналог «папок»). Категория — заголовок группы; под ним список кейсов этой категории.
- В **списке по каждой категории** показывать только **заголовок кейса** (`title`), статус (бейдж: draft / pending_review / approved / archived) и при необходимости дату обновления. Полный контент (questions, keywords, response_template и т.д.) в списке не показывать.
- **Фильтры над списком:** статус (множественный выбор или один), категория (для быстрого сужения), «только мои» (mine=true — кейсы, созданные текущим principal). Запрос: `GET /api/v1/cases` с query-параметрами по OpenAPI.
- Кнопки: «Создать кейс», «Импорт», «Экспорт» (см. ниже). При выборе «Экспорт» — диалог или форма с фильтрами (category, status), затем `GET /api/v1/cases/export` и сохранение ответа как JSON-файл.

### Просмотр одного кейса (детальный вид)

- По **клику на заголовок** кейса в списке открывать экран/панель **детального просмотра**: все поля кейса (category, title, questions, keywords, response_template, status, created_by, даты, notes). То есть «весь чанк» виден только здесь, не в списке.
- На экране детального просмотра кнопки/действия:
  - **Редактировать** — переход к форме редактирования (те же поля, что в CaseUpdate: category, title, questions, keywords, response_template, notes). Сохранение → `PUT /api/v1/cases/{id}`.
  - **Сменить статус** — форма с полем статуса (draft → pending_review, pending_review → approved/draft, approved → archived) и опционально comment. Отправка → `POST /api/v1/cases/{id}/status`.
  - **Удалить (архивировать)** — подтверждение, затем `DELETE /api/v1/cases/{id}`.
- Для draft-кейсов правила доступа по API (только создатель) не меняются; при 403 показывать сообщение об ошибке.

### Создание кейса

- Форма по схеме CaseCreate: category, title, response_template (обязательные), questions, keywords (массивы строк, по умолчанию пустые). Отправка → `POST /api/v1/cases`. После успеха — переход к списку или к созданному кейсу (детальный вид).

### Импорт кейсов

- Кнопка «Импорт»: выбор файла (JSON), выбор режима (merge / draft / replace) по описанию из OpenAPI. Отправка → `POST /api/v1/cases/import` с телом из файла и query-параметром mode. Отображение результата (imported, updated, errors из ответа API).

### Экспорт кейсов

- Кнопка «Экспорт»: выбор фильтров (category, status), затем `GET /api/v1/cases/export` и сохранение ответа как файл с именем, содержащим дату/время (уточнение 4), например `cases-export-2025-02-17.json`.

## Раздел «Тикеты» — только Staff

### Список тикетов

- Таблица или карточный список: колонки/поля — запрос (query, обрезанный по длине), категория, статус, назначен (assigned_to), дата создания. Полный текст запроса и resolution_notes в списке не показывать.
- **Фильтры:** статус, категория (по OpenAPI для `GET /api/v1/tickets`).
- Кнопка «Создать тикет вручную». По клику на строку — открыть детальный просмотр тикета.

### Просмотр одного тикета (детальный вид)

- По клику — экран с полными данными: query, category, confidence, status, assigned_to, даты, resolution_notes, converted_to_case_id (и ссылка на кейс, если есть).
- Действия:
  - **Редактировать** — форма по TicketUpdate (status, assigned_to, resolution_notes). Сохранение → `PUT /api/v1/tickets/{id}`.
  - **Конвертировать в кейс** — форма с опциональными полями title, category, response_template (по ConvertToCaseRequest). Отправка → `POST /api/v1/tickets/{id}/convert-to-case`. В ответе отобразить case_id и url; предложить переход к созданному кейсу в разделе «База знаний».

### Создание тикета вручную

- Форма: query (обязательно), category, confidence (опционально). Отправка → `POST /api/v1/tickets`. После успеха — переход к списку или к созданному тикету.

## Раздел «Приложения» — только Staff

- **Список приложений:** название (name), id, при необходимости даты. По клику — переход к детальному просмотру/редактированию приложения.
- **Детальный просмотр приложения:** поля App (name, id, created_at, updated_at), блок **«Настройки»** — отображение и редактирование `settings` (GET/PUT `/api/v1/apps/{id}/settings`). В первой версии: явные поля для `search.default_top_k` и `search.confidence_threshold`; остальные ключи — только read-only (сырой JSON или список), без полноценного JSON-редактора (уточнение 7).
- Кнопки: **Экспорт настроек** (`GET /api/v1/apps/{id}/settings/export`) — сохранение файла; **Импорт настроек** — выбор JSON-файла, отправка `POST /api/v1/apps/{id}/settings/import` (полная замена).
- **Создание приложения:** форма по AppCreate (name, опционально settings). Отправка → `POST /api/v1/apps`. Редактирование приложения → `PUT /api/v1/apps/{id}` (name, settings).
- Создание токенов для приложения в текущем API не предусмотрено; при появлении в OpenAPI эндпоинта создания токена — в этом разделе добавить подраздел или форму «Создать токен» для выбранного приложения.

## Ошибки API

- Любой ответ с кодом 4xx/5xx отображать в едином виде: HTTP-код, `error.code`, `error.message`, при наличии — `error.details`. Не менять контракт в 00–08; UI только читает и показывает эти поля. Место показа — тост, баннер над контентом или модальное окно (одно на всё приложение). **При 401** дополнительно показывать ссылку или кнопку «Перейти в Настройки и обновить токен» (уточнение 6).

- Каталог: **`web/`** в корне проекта (уточнение 8). Сборка SPA (если используется) — артефакт в `web/dist/` или аналог.
- Раздача: в рамках задачи не обязательно встраивать раздачу в 08; достаточно SPA, раздаваемого отдельным сервером или nginx. Добавление в 08 маршрута вида `GET /app/*` → статика из `web/dist/` опционально (уточнение 5). Модули 00–08 не меняем, кроме опционального обработчика статики в 08.

## Отчёт о реализации (handoff)

### Реализовано

**Стек:** React 18 + Vite + TypeScript, React Router. Каталог: `web/`, артефакт сборки: `web/dist/`.

**Настройки**
- Поля: Bearer token, базовый URL API. Пустой URL → `window.location.origin + '/api/v1'`.
- Кнопка «Сохранить в браузере» пишет в localStorage (`demo_token`, при необходимости базовый URL).
- Тип доступа (App/Staff): только отображение; определяется при старте запросом `GET /api/v1/cases?limit=1` (200 → Staff, 403 → App).

**Поиск**
- Форма: query (обязательно), category, top_k, user_context (одно textarea с JSON).
- Результаты: чанки (заголовок, фрагмент, по клику — полный текст, confidence); при наличии — блок с тикетом и ссылкой в раздел «Тикеты».

**База знаний (Кейсы), только Staff**
- Список с группировкой по категориям, фильтры: статус, категория, «только мои».
- Кнопки: Создать кейс, Импорт, Экспорт (имя файла с датой/временем).
- Детальный просмотр: все поля; действия: Редактировать, Сменить статус, Удалить (архивировать).
- Создание, редактирование, смена статуса, импорт (merge/draft/replace), экспорт по фильтрам.

**Тикеты, только Staff**
- Список (таблица), фильтры по статусу и категории, «Создать тикет вручную».
- Детальный просмотр; Редактировать (status, assigned_to, resolution_notes), Конвертировать в кейс (опциональные title, category, response_template).

**Приложения, только Staff**
- Список, создание, детальный просмотр.
- Настройки: редактируемые поля `search.default_top_k` и `search.confidence_threshold`; остальные ключи — read-only (JSON).
- Экспорт/импорт настроек (файл JSON).

**Ошибки API**
- Единый формат: HTTP-код, error.code, error.message, при наличии — error.details. При 401 — ссылка «Перейти в Настройки и обновить токен».

**Навигация**
- Боковое меню: Поиск (всегда), База знаний, Тикеты, Приложения (только при Staff), Настройки.

### Запуск и сборка

- Запуск: `cd web && npm install && npm run dev`.
- Сборка: `npm run build`.
