# Предложения: дружественное отображение шаблонов ответа (response_template)

## Цель

Во всех местах, где редактируется шаблон ответа (Go `text/template`), показывать типовые конструкции по-русски и наглядно (выделение, при наведении — исходный код). Неподдерживаемый код выделять курсивом. Рассмотреть вариант визуального конструктора.

## Где используется поле шаблона

- **Создание кейса** — `web/src/pages/Cases/Create.tsx`, поле `response_template`
- **Редактирование кейса** — `web/src/pages/Cases/Edit.tsx`, поле `response_template`
- **Конвертация тикета в кейс** — `web/src/pages/Tickets/Convert.tsx`, опциональное поле `response_template`
- **Просмотр кейса** — `web/src/pages/Cases/Detail.tsx`, только отображение (без редактирования)

Во всех формах сейчас одно текстовое поле (textarea или input) с сырым текстом шаблона.

## Поддерживаемый подмножество (для «понятного» отображения)

Ограничиваемся конструкциями без циклов и без вызовов произвольных функций:

| Код шаблона | Человекочитаемая подпись (RU) | Выделение |
|-------------|------------------------------|-----------|
| `{{.field}}` | Подставить поле «field» | жирным |
| `{{if .field}}...{{end}}` | Если поле «field» указано — … | жирным блок «Если … указано» |
| `{{if not .field}}...{{end}}` | Если поле «field» не указано — … | жирным |
| `{{if eq .field "value"}}...{{end}}` | Если «field» равно «value» — … | жирным |
| `{{if eq .field "value"}}...{{else}}...{{end}}` | Если «field» равно «value» — … иначе … | жирным оба варианта |
| Вложенные `{{if}}` с теми же правилами | Рекурсивно разбирать, подписи вложенных условий | жирным |
| Любой другой фрагмент `{{...}}` | Не разбираем | курсив (исходный код как есть) |

Обычный текст (вне `{{}}`) не трогаем.

## Варианты реализации

### Вариант A: «Просмотр с подсказкой» (минимальный)

- В формах создания/редактирования/конвертации оставляем **одно поле** — как сейчас, обычный textarea с сырым шаблоном.
- **Рядом** (или под полем) — блок **«Как будет выглядеть»**: тот же шаблон, но с заменой **распознанных** конструкций на короткие подписи на русском в **жирном** шрифте, нераспознанные `{{...}}` — **курсивом**. Это только отображение, не редактирование.
- При **наведении** на подпись в блоке «Как будет выглядеть» показывать tooltip с исходным кодом (например `{{.phone}}`).
- Плюсы: быстро реализовать, один парсер на отображение, не трогаем логику сохранения. Минусы: редактирование по-прежнему только в коде.

**Реализация:** один React-компонент (например `TemplatePreview`), принимает `source: string`, парсит по регулярным выражениям или по простому конечному автомату (найти `{{`, затем `}}`), для каждого фрагмента между `{{` и `}}` определить тип (`.field`, `if .field`, `if eq .field "x"`, `else`, `end`, иначе — «другое») и отрисовать либо жирную подпись, либо курсивный код. Tooltip — через `title` или библиотеку тултипов.

---

### Вариант B: Inline-подсветка в том же поле (contenteditable или замена при фокусе)

- Поле ввода остаётся одним, но **в режиме просмотра** (например по умолчанию или по кнопке «Показать понятно») текст в нём рендерится как разметка: распознанные конструкции — жирные span’ы с `title` с исходным кодом, нераспознанные — курсив.
- По **клику** на блок или при **фокусе** на поле — переключаться в «режим кода»: показывается сырой шаблон для редактирования. При снятии фокуса — снова «понятный» вид (или оставить режим переключаемым кнопкой).
- Плюсы: одно место, и просмотр, и переход к редактированию. Минусы: contenteditable капризен (курсор, вставка), проще сделать не contenteditable, а два режима: либо текстовая область с кодом, либо div с подсвеченными span’ами (только чтение), по клику «Редактировать» — показать textarea.

**Реализация:** два состояния — `previewMode` и `editMode`. В previewMode — разбить шаблон на токены, отрисовать div со span’ами (жирный/курсив + tooltip). В editMode — обычный textarea. Кнопка «Редактировать» / «Показать как код» переключает режим и подставляет в textarea актуальное значение.

---

### Вариант C: Два поля — «код» и «как видно»

- Два блока: **1)** текстовое поле с шаблоном (как сейчас); **2)** под ним блок «Для пользователя» с тем же содержимым, но с жирными подписями и курсивом для неизвестного кода. При наведении на подпись — tooltip с кодом.
- Редактирование только в первом поле; второй только для чтения и обновляется при изменении первого (onChange).
- Плюсы: просто и предсказуемо, без переключения режимов. Минусы: занимает больше места по вертикали.

**Реализация:** общий компонент формы (или HOC), внутри — textarea + компонент из варианта A ниже него.

---

### Вариант D: Визуальный конструктор (блоки)

- Шаблон представляется как **последовательность блоков**: «Текст», «Подставить поле X», «Если X указано — …», «Если X равно "Y" — … иначе …». Редактирование: добавлять/удалять/менять блоки, менять порядок (drag-and-drop или кнопки вверх/вниз).
- При сохранении формы блоки **сериализуются** в один строковый шаблон и уходят в API как `response_template`.
- Поддерживаемый набор блоков на первом этапе: (1) произвольный текст, (2) подстановка поля, (3) условие «если поле указано», (4) условие «если поле равно строке» с веткой «иначе». Вложенность: внутри «иначе» или «то» могут быть такие же блоки (рекурсия).
- Плюсы: максимально понятно для нерусифицированного пользователя, нет синтаксиса. Минусы: нужно парсить существующие шаблоны в блоки (при открытии формы) — возможны шаблоны, которые не удаётся разобрать; тогда показывать «режим кода» или только текст с предупреждением.

**Реализация:**  
- Парсер строки шаблона → AST (дерево блоков: text, variable, if_exists, if_equals, else). Парсер только для описанного подмножества; при встрече `range`, `with`, вызовов функций и т.п. — считать ветку «неразобранной» и хранить как один текстовый блок.  
- UI: список блоков, каждый блок — карточка с полями (для «если равно» — поле, значение, подблоки «то»/«иначе»). Кнопки «Добавить блок», «Удалить», «Вверх/Вниз». Внизу или в отдельной вкладке — «Исходный код» (readonly), чтобы видеть итоговую строку.  
- Обратная конвертация: AST → строка шаблона по правилам Go text/template.

---

### Вариант E: Гибрид — конструктор + «сырой» режим

- По умолчанию форма показывает **визуальный конструктор** (вариант D), если шаблон **удалось разобрать** в блоки.
- Кнопка **«Редактировать как код»** переключает в одно текстовое поле с сырым шаблоном; при переключении обратно в «конструктор» делается попытка распарсить — если не вышло, показывать предупреждение и оставить в коде или показать конструктор с одним «сырым» блоком.
- Для новых кейсов по умолчанию можно показывать конструктор с пустым списком блоков.
- Плюсы: удобно и наглядно там, где хватает конструктора; сложные шаблоны можно править в коде. Минусы: самая большая трудоёмкость (парсер туда-обратно, два UI).

---

## Рекомендации по внедрению

1. **Сначала реализовать вариант A или C** (парсер только для отображения, без изменения способа редактирования). Это даёт быстрый выигрыш: пользователь видит «как будет выглядеть» и при наведении — код. Места внедрения: Create Case, Edit Case, Convert to Case; при желании — Detail в режиме только просмотра.
2. **Парсер «подписей»** сделать в виде одной утилиты (например `parseTemplateForPreview(tpl: string): Array<{ type: 'text'|'variable'|'if_exists'|'if_equals'|'unknown', raw?: string, label?: string }>`) и использовать её и в A, и в C, и позже в D/E.
3. **Визуальный конструктор (D или E)** планировать вторым этапом: после стабилизации подмножества конструкций и формата AST описать контракт «строка ↔ блоки» и реализовать UI блоков с сериализацией в строку.

## Технические детали парсера подписей

- Обход строки посимвольно или по токенам: ищем `{{` и `}}`, извлекаем внутреннюю часть.
- Внутри `{{...}}` убираем пробелы по краям, затем:
  - если совпадает с `\.\w+` — «Подставить поле "X"»;
  - если начинается с `if ` и затем `.\w+` и только `end` — «Если поле "X" указано»;
  - если `if not .\w+` … — «Если поле "X" не указано»;
  - если `if eq .\w+ "..."` (или `'...'`) — «Если "X" равно "..."»;
  - `else` — «иначе»;
  - `end` — не выводить отдельно или «конец условия»;
  - иначе — тип `unknown`, выводить курсивом как есть.
- Вложенность для подписей можно не строить в первом варианте — достаточно показывать последовательность фрагментов жирным/курсивом; для конструктора понадобится полноценный AST.
